# Pinzos 整体架构图解(简明版)

> 目的:用图 + 大白话,让你一眼看懂整个系统怎么串起来、新功能插在哪。
> 日期:2026-05-15 · 配套:`pinzos-design-spec.md`、`pinzos-feature-transaction-truth-spec.md`、`pinzos-feature-agent-portal-spec.md`
> 已拍板决策:数据**定时更新(每周同步),不做实时**。

## 1. 系统总览:谁和谁说话

```
                        ┌──────────────────────────────────────┐
                        │        前端 Frontend (React+Vite)     │
                        │  地图 / 项目详情 / 成交查询页          │
                        │  价格体检 / 经纪报告工作台             │
                        │  Luna 语音助手(浏览器直连 Gemini)    │
                        └────────────────┬─────────────────────┘
                                         │  HTTPS / SSE
                        ┌────────────────▼─────────────────────┐
                        │      主 API 服务 (Express, cpx11)     │
                        │  REST 接口 · 鉴权/角色 · SSE 进度     │
                        │  ┌────────────────────────────────┐  │
                        │  │  market-analytics(共享计算层) │  │ ◄── 所有"判断"都走这里
                        │  │  报告生成 report generator      │  │
                        │  └────────────────────────────────┘  │
                        └───┬──────────────┬─────────────┬─────┘
                            │              │             │
              ┌─────────────▼───┐   ┌──────▼──────┐  ┌───▼──────────────┐
              │  PostgreSQL     │   │  Worker     │  │  Cloudflare R2   │
              │  dld_* 成交/租约 │   │ (cpx32)     │  │  楼书 PDF / 图片 │
              │  areas 区域指标  │   │ PDF 提取    │  └──────────────────┘
              │  projects 项目   │   │ LangGraph   │
              │  users / subs   │   │ 7 个 agent  │
              └────────▲────────┘   └─────────────┘
                       │
            ┌──────────┴──────────────┐
            │  定时同步任务(每周)    │  ◄── 本次新增的核心地基
            │  Dubai Pulse 开放数据   │
            └─────────────────────────┘
```

**大白话**:前端只管显示和交互;主 API 是大脑,所有"这房贵不贵、这区怎么样"的判断都收口到一个 `market-analytics` 共享层(避免每个功能各算各的);Worker 专门啃 PDF 楼书这种重活;PostgreSQL 存所有数据;**每周一个定时任务**去把迪拜官方成交数据拉下来洗干净——这是所有信任功能的地基。

> 这套两服务器(主 API + Worker)架构是项目现有的,见根目录 `CLAUDE.md`。新功能不改架构,只是在主 API 里加 `market-analytics` 层 + 加一个定时同步任务。

## 2. 数据定时更新管线(已拍板:每周,非实时)

> 实测结论:dubaipulse.gov.ae 只放行 UAE 网络,德国服务器连不上;DLD 付费 API 企业级不可行。
> 故必须经 **UAE 出口** 拉 Dubai Pulse 开放数据。服务费无免费源,走楼书/人工。

```
 来源(免费公开)            UAE 出口             每周定时任务
 ┌────────────────────┐   ┌──────────────┐
 │ Dubai Pulse 成交   │──►│ UAE VM/代理  │──┐  (绕过地理封锁)
 │ Ejari 租约         │──►│ 仅负责抓取   │──┤
 │ 住宅价格指数       │──►│ 回传主库     │──┘
 └────────────────────┘   └──────────────┘
   服务费 Mollak ✗ 无免费源 → 由功能 F 楼书提取/人工补(标估算)
            │
            ▼
   ① 拉取 Ingest ───────────► 记录"数据截止日" data_vintage
            │
            ▼
   ② 清洗 Clean(护城河)──► 项目名归一化 · 去重 · 期房/二手分离
            │                 · 剔除赠与/关联方非市场交易
            ▼
   ③ 计算 Aggregate ───────► 中位数价 · 真实净收益 · 溢价拆解
      (market-analytics)      · 区域分级 · 开发商交付评分
            │
            ▼
   ④ 落库 + 时点标注 ──────► 指标表 + "数据截至 YYYY-MM-DD"
            │
            ▼
   被这些功能消费:B 成交查询 · D 价格体检 · C 区域判断 · E 投资报告
```

**为什么是每周不是实时**:迪拜官方数据本身有 4–8 周登记滞后,实时不存在;每周同步足够,且每个数字旁标注"数据截至某日"——诚实比假装实时更可信。**清洗(第②步)是真正的护城河**,原始数据谁都能免费拿,洗干净并能解释才是壁垒。

## 3. 成交真相功能:一次查询怎么流动

```
买家点开"项目详情 / 成交查询"
        │
        ▼
前端 ──GET /api/market/price-check?project=X──► 主 API
                                                  │
                                                  ▼
                                       market-analytics(读已洗好的指标表)
                                                  │
                ┌─────────────────┬───────────────┴────────┐
                ▼                 ▼                        ▼
          成交中位数        期房 vs 二手溢价          真实净收益
                └─────────────────┬────────────────────────┘
                                  ▼
                        差距解释器(中性措辞)
                                  ▼
   ◄── JSON: {标尺区间, 本项目价位点, 红黄绿, 解释文案, 数据时点} ──
                                  │
                                  ▼
        价格体检 UI:绿/黄/红标尺 + "为什么差这么多?" 可展开
```

**大白话**:用户打开一个项目,前端问 API "这价合理吗",API 从洗好的数据里算出中位数/溢价/净收益,再套一层"为什么门户价≠官方价"的解释,返回给前端画成一根红黄绿标尺。买家最痛的"我是不是被宰了"在这一步被提前解答。

## 4. 经纪人接口与订阅:架构

```
经纪人 / 开发商 注册
        │ 选角色
        ▼
   Supabase Auth(扩展角色)
   roles: agent | developer | agency-admin | platform-admin
   subscription: 试用(14-30天) → 个人版/团队版 → 到期降级
        │
        ▼
   经纪报告工作台(前端)
        │ 选 区域 / 项目 / 客户目标(投资·自住·兼具)
        ▼
   报告生成器(主 API)── 全部复用,不重造 ──┐
        ├── market-analytics  → 功能 C 区域分级 / D 价格体检
        ├── investment-calculator → 功能 E 5年测算(区间+免责)
        └── 品牌注入(logo/RERA/联系方式)+ 多语言(EN/AR/RU/ZH)
        ▼
   导出 PDF / 可分享链接
        ▼
   支付(Stripe / Telr / Network)月付 · 无锁定

   ⚠ 买家端信任功能(B/C/D)始终免费,不进此付费墙
```

**大白话**:经纪人订阅卖的不是新数据,而是把买家端已有的判断能力"打包成带他自己品牌的客户报告"。所有内容复用 market-analytics 和投资计算器,所以这个模块本身很薄——它依赖前面的功能先做好,否则没东西可卖。

## 5. 功能依赖与优先级(一张图看清先做什么)

```
P0 速赢   卫星底图 · 首页区域名+指标 · 地图测距
          (互相独立,不阻塞别人,先上给开发商演示)

          ┌──────────────────────────────────────────────┐
P1 地基   │  ★ 数据定时同步 + 清洗(本架构第 2 节)        │
          │  ★ 功能 F 楼书提取质量 + 人工修正             │
          └───────────────────────┬──────────────────────┘
                                   │  (数据不准 = 上面全白做)
                                   ▼
P1 信任    功能 B 成交查询 ──► 功能 D 价格体检 ──► 功能 C 区域判断
                                   │
                                   ▼
P1 决策             功能 E AI 买房决策报告(区间 + 免责)
                                   │
                                   ▼
P2 商业化   功能 G 经纪订阅 + 开发商演示模式
            前置:B/C/D/E 必须先成型,否则订阅无内容可卖
```

**一句话排序逻辑**:先做不阻塞别人的速赢 → 再修地基(数据清洗 + 楼书提取,不然信任功能建在沙子上)→ 再做信任三件套 → 再做决策报告 → 最后才商业化。

## 6. 关键约束(贯穿所有功能,别违反)

1. **数据每周定时更新,不承诺实时**;每个数字标注"数据截至某日"。
2. **所有判断收口到 `market-analytics` 一个共享层**,不允许各功能各算一套。
3. **买家端信任功能永久免费**,商业化只在经纪人端。
4. **措辞中性**:给可解释因素,不说"你被宰了"(平衡买家信任与开发商=供给方)。
5. **预测给区间(保守/中性/乐观)+ 免责**,不给单一"稳赚"数字。
6. **不抢线索、不自建挂牌门户**(门户垄断分发,正面竞争必败)。
