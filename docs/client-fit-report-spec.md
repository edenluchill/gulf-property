# 客户分析报告（Client Fit Report）—— 重做 Spec

> 2026-07-12 · 状态：待实施
> 现名「秒出提案」(`/agent/report`) → 改为「**客户分析报告**」

---

## 0. 定性：AI 的活是「论证」，不是「选盘」

> owner 原话：**「用 AI 来解释清楚为啥适合客户、特点是什么、为啥值得 —— 说服客户」**
> 补充：**「要用特点对特点，一个户型要读懂客户的情况，要做 2 层深层分析和挖掘」**

**这句话说明现在的实现方向是错的。**

现在的 `auto-match.ts / matchProperties()` 是让 **AI 替经纪选盘**（从 90 个候选项目里挑 3 个）。
但**经纪心里早就知道要推哪个项目** —— 他缺的不是「选哪个」，是「**怎么说服客户这个值得**」。

| | 现在 | 应该 |
|---|---|---|
| AI 干什么 | 从 90 个项目里挑 3 个 | **论证「这个项目/这个户型为什么适合这个客户」** |
| 经纪输入 | 两个自由文本框（名字 + 一段画像） | **选客户（CRM 自动带画像）+ 选项目 + 选户型** |
| 「适合的户型」 | ⚠️ **最便宜的 8 个（假的）** | 按他的预算/几居/家庭真匹配 + **逐条论证为什么** |

### 「客户画像太难填」的答案：**根本不该让经纪填**

`lt_clients` 里**已经有全套字段**，经纪却在报告页从零手打一段自由文本：

```
goal · budget_min/max/budget · bedrooms · family_size · has_children
preferred_areas · preferences · nationality · preferred_language
expectations · traits · background · notes
```

→ **选一个 CRM 客户，画像全部自动带出。** 缺的字段用 chips 快速补（不打字）。

## 1. ⚠️ 数据现实（决定 AI 能咬什么，别让它编）

`project_unit_types` 实测填充率（468 行）：

| 字段 | 填充率 | 能用? |
|---|---|---|
| `bedrooms` / `bathrooms` / `area` | **100%** | ✅ 核心 |
| `features`（数组） | **100%** | ✅ **金矿,见 §2** |
| `floor_plan_image` | 100% | ✅ 报告里放图 |
| `balcony_area` | 88% | ✅ |
| `price` / `price_per_sqft` | ⚠️ **51%** | ⚠️ 半数缺价 → 见 §4 |
| **`orientation`（朝向）** | ❌ **0%** | ❌ **绝不能进 prompt** |
| **`view_type`（景观）** | ❌ **0%** | ❌ **绝不能进 prompt** |
| **`floor_level`（楼层）** | ❌ **0%** | ❌ **绝不能进 prompt** |
| `parking_spaces` | ❌ 3% | ❌ |

> 🔴 **硬约束**：朝向 / 景观 / 楼层 / 车位 **一律不写进 prompt**。
> 给 AI 一个空字段，它就会开始编 —— 而这份报告是要**发给客户**的，编一句「南向采光好」
> 就是在经纪的品牌上撒谎。**没有的数据,就不提。**

而现在的 `projectUnits()` 只 `SELECT unit_type_name, bedrooms, area, price, price_per_sqft` ——
**把 100% 填充的 `features`、`bathrooms`、`balcony_area`、`floor_plan_image` 全丢了**。
AI 想「特点对特点」也无米下锅。

## 2. `features` 是「特点对特点」的原料

实测 Top 特征（`unnest(features)`）→ **每一条都能读出客户的处境**：

| 户型特征 | 出现 | 读出客户的什么 |
|---|---|---|
| **Maid's room** + Maid's bathroom | 194 / 126 | 中东/亚洲**大家庭刚需** —— 有小孩、family_size 大 |
| Laundry room | 256 | **长期自住**信号（投资客不在乎） |
| Storage / Utility room | 65 / 70 | 长期自住、家当多 |
| **Open kitchen** | 277 | ⚠️ 对**中国客户可能是减分项**（炒菜要封闭厨房）← **这才叫读懂客户** |
| Walk-in closet / Dressing room | 144 / 106 | 高端自住 |
| **Powder room**（客用卫生间） | 332 | 常**接待客人** |
| En-suite bathroom | 281 | 多代同住 / **好分租**（投资） |
| Private terrace / Multiple balconies | 96 / 132 | 户外空间需求 |
| Master bedroom | 242 | — |

> 反向论证也要做：**为什么不推那个更便宜的户型** —— 比如「B2 便宜 8 万，但没有女佣房，
> 你们一家四口 + 保姆住不开」。**说清楚不推什么，比只夸一个更有说服力。**

## 3. 两层深度分析（AI 的输出结构）

### Layer 1 — 项目 × 客户
| 项目侧（已有数据） | 客户侧 |
|---|---|
| 区域 area_metrics（中位价/租金回报/涨幅） | budget · goal（自住/投资） |
| 真实 DLD 成交 comps | expectations（他要什么） |
| 周边 POI（学校/地铁/医院/商场） | has_children · family_size · preferred_areas |
| 开发商 · 交付时间 · 付款计划 | traits · background · notes |
| 5 年净回报测算（已有 `netProfit`） | — |

输出：**匹配度（0-100）+ 3-5 条「为什么适合你」+ 1-2 条「你需要知道的风险/取舍」**
（诚实的取舍比全是优点更可信 —— 客户不傻）

### Layer 2 — 户型 × 客户（**特点对特点，逐条**）
对每个候选户型：
- 面积 vs family_size（住得开吗）
- bedrooms vs family_size + has_children
- **features 逐条咬合**（见 §2 的映射表）
- 总价 vs budget（付款计划要不要提）
- price_per_sqft vs 区域中位单价（贵/便宜多少，值不值）
- 投资客：租金回报 / 好不好出租 / 好不好转手

输出：**推荐 1 个主推户型 + 逐条论证 + 「为什么不推另外那个」**

## 4. ⚠️ 价格缺失（51%）怎么办

半数户型 `price IS NULL`。现在的 `projectUnits()` 直接 `WHERE price IS NOT NULL` **把它们全过滤掉了** ——
所以经纪看到的「适合的户型」可能根本不含真正适合的那个（只是它没录价）。

**处理**：
- 无价户型**照常参与匹配**（bedrooms/area/features 都有），但：
  - 预算维度标注「**价格待定，需向开发商询价**」
  - 不参与「总价 vs 预算」的论证，也不让 AI 猜价格
- 报告里显示「价格待定」而不是隐藏 —— 隐藏 = 经纪不知道有这个户型

## 4.5 ⭐ 客户画像 = 引导式 process，不是表单（owner 2026-07-12 定）

> **「做成一个 process 吧，引导性的，AI 会智能提问帮他们优化缺少什么描述，
> 能有足够完整的信息才能生成更精准的匹配」**

把「填画像」从**表单问题**变成**对话问题**。而且它有个超出数据收集的价值：

> 🎯 **AI 问的问题本身，就在教经纪该去问客户什么。**
> 很多经纪根本没想过要问「你们家平时做饭吗」—— 而这个问题直接决定
> open kitchen（277 个户型有）是**加分还是减分**。

### 🔴 铁律：答案必须**回写 `lt_clients`**

不回写，经纪每次生成报告都要重答一遍 —— 那只是换了个形式的「太难填」。
回写之后：**问过一次，永久受益**，CRM 画像也顺带被补全了（一石二鸟）。

### 两段式（规则打底 + AI 深挖）

**第一段 —— 规则层（零 LLM 成本、瞬时）**
检测**硬字段**缺失，用 chips 补，不打字：

| 字段 | 权重 | 缺了会怎样 |
|---|---|---|
| `goal`（自住/投资） | **25** | 整个论证的地基 —— 投资看回报，自住看住得舒不舒服 |
| `budget` / `budget_max` | **25** | 没预算 → 户型匹配无从谈起 |
| `bedrooms` | 15 | — |
| `family_size` + `has_children` | 15 | 决定 Maid's room / Laundry / 学区 咬不咬得上 |
| `preferred_areas` | 10 | — |
| `nationality` | 10 | 决定 open kitchen 这类**文化维度**能不能用 |

→ 画面上给一个**完整度进度条**：「画像完整度 60% —— 再补 2 项可到 90%，匹配会准很多」

**第二段 —— AI 深挖（1 次 LLM 调用，出 2-3 个问题）**
基于**已有信息**动态提问，专挖「特点对特点」需要的**软信息**（结构化字段里没有的）：

```
陆先生 · 投资 · 300万 · 一家四口
→ AI 追问:
  ① 「投资是想长期收租，还是 3-5 年转手？—— 这决定推 1 房还是 2 房」
  ② 「一家四口，孩子多大？要不要考虑学区？」
  ③ 「有请保姆吗？—— 迪拜很多户型带女佣房，没有的话会住得很挤」
```

每个问题给 **chips 快选 + 可选自由补充**（还是不打字）。
问题数**上限 3 个**（问多了经纪就跑了），答完直接生成。

### 复用：建客户时也走同一个 wizard
同一个 `ClientProfileWizard` 组件，两处挂：
- **客户雷达**建客户时 → 一开始就把画像问全（之后所有工具都受益）
- **报告页**选了画像不全的客户时 → 就地补

### Phase 2（不在本次 scope）：让**客户自己答**
生成一个问卷链接发给客户 → 客户自己勾 → 画像补全 + 报告自动生成。
比经纪转述更准，且**知道人是谁**（呼应 [[leads-tab-parked]]：有身份的意向才有用）。

## 5. 输入端重做（`/agent/report`）

```
┌─ 客户 ────────────────────────────────┐
│ [ 从客户雷达选 ▾ ]  或  [ + 新客户 ]   │   ← CRM 下拉,选完自动带出画像
│                                        │
│ 陆先生 · 投资 · 300万 · 2房 · 一家四口 │   ← 画像预览(可点开改)
│ 偏好: Dubai Creek Harbour, JVC         │
│ ⚠️ 缺: 有无小孩  [有] [无]             │   ← 缺字段用 chips 补,不打字
└────────────────────────────────────────┘
┌─ 项目 ────────────────────────────────┐
│ [ 搜索项目… ]  Creek Bay ✕             │   ← 经纪手选(他知道要推什么)
│ ☐ 让 AI 帮我推荐（不确定推哪个时）      │   ← 保留 matchProperties 作为可选兵器
└────────────────────────────────────────┘
┌─ 户型（可选）──────────────────────────┐
│ ☑ TOWER A 1BR A1  764ft² · ⌂179万      │   ← 不选 = AI 从全部里挑并说明理由
│ ☐ TOWER B 1BR B2  761ft² · ⌂179万      │
└────────────────────────────────────────┘
        [ 生成分析报告 ]  20 积分
```

**决策（owner 2026-07-12 定）**：
- ✅ **单项目深度说服**（火力集中；截图里那份 Creek Bay 就是这个形态）
- ✅ **保留 AI 选盘作为可选兵器**（经纪不选项目时才跑 `matchProperties`）

5. **收尾**：demo 样板报告 + 全站改名
