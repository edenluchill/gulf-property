# Area Blocks 防盗保护 —— 分析与设计（待 pickup）

> 状态：设计草案，未实现。2026-06-27 创建。
> 背景：`dubai_areas.boundary` 区域多边形是同事手工绘制的专有 IP。诉求是「至少
> network trace 拿不到、不能简单破解」——即**提高复制门槛**，而非绝对防住。

---

## 1. 要保护的资产 + 威胁模型（先定清楚，否则方案没法选）

**资产**：`dubai_areas` 的 `boundary`（高精度多边形坐标）——同事画的，是劳动成果。
注意：区域的**名称/指标**是 DLD 公开数据，不算 IP；要保护的是**几何形状**本身。

**威胁分级**（决定要做到哪一档）：

| 级别 | 攻击者 | 手段 | 现状能挡吗 |
|---|---|---|---|
| T1 低 | 随手党/初级竞品 | 打开 devtools，network 里看到干净 GeoJSON,复制 | ❌ 现在裸奔，一键复制 |
| T2 中 | 会写脚本的人 | 跑你的解密函数 / 读渲染后地图 source / headless dump | 加密也挡不住 |
| T3 高 | 认真竞品 | 栅格瓦片也能描图重画（费时失真） | 只能提高成本+法律 |

**关键判断**：现实可达的目标是「**挡住 T1、把 T2 的成本从几分钟抬到几小时、对 T3 靠成本+水印+法律**」。没有任何技术能对 T3 绝对防住——**凡是前端渲染出来的，就能被还原到某种精度**。

---

## 2. 为什么「客户端解密」从根上防不住（务必理解，别白做功）

- 前端要能渲染就必须能解密 → **解密密钥+逻辑必然打包进浏览器** → 完全可读可运行。
- 攻击者**不需要破解密码学**，三条任意一条即可拿到：
  1. devtools 里读**解密后**的 network 响应 / 内存对象；
  2. 控制台直接**调用你自己的解密函数**；
  3. 从地图引擎读已渲染数据：MapLibre `map.getSource(id)._data` / `querySourceFeatures()` 直接吐出 GeoJSON。
- **密钥轮换无用**：爬虫每次跟你前端一样去取当前密钥。
- **非对称用错方向**：用户最初设想「私钥加密/公钥解密」= **数字签名,零保密**（公钥人人有→人人能解）。真要保密得「公钥加密/私钥解密」，但私钥若在前端就不再是秘密 → 回到上面的死结。

> 结论：**对称/非对称/轮换都一样,客户端解密 = 障眼法(obfuscation),只挡 T1、拖慢 T2,不挡 T3。**

---

## 3. 方案（三档，可叠加）

### ⚠️ 先澄清一个常见误区：瓦片是「离线预生成」，不是「每请求现渲染」

服务端瓦片化 **≠ 每个用户每次访问都现场画地图**（那确实会压垮服务器）。而是：
- **建库时离线生成一次**：跑个脚本把 210 个区在各缩放级别烤成一堆静态小文件（PNG/MVT），存到 R2/磁盘。区域边界基本永不变 → 生成一次就长期复用，只有同事编辑了区域才重烤（可只烤受影响瓦片）。
- **运行时只发静态文件**：nginx / R2 / Cloudflare 发现成的小图，跟发一张 logo 一样轻，且**可边缘缓存 → 几乎不碰 origin**。
- **运行时负担不增反降**：比现在每次返回 672KB + DB 聚合的 `/dubai/areas` 轻得多。唯一「活」的计算是点区时一次 `ST_Contains`（毫秒级）。

类比：把地图**导出成图片存好**，以后发图片，不是每个访客来了重画。Mapbox/Google 地图都这么干。

### 方案 A —— 不把坐标发给浏览器：服务端瓦片化（**真·防 network trace，推荐**）

把区域块在**服务端渲染**，前端只收到不含原始坐标的产物：

- **A1 栅格瓦片(PNG)**：用服务端渲染区域填充/描边成 256×256 PNG 瓦片（MapLibre/Mapbox GL 作为 raster source 叠加）。Network 里只有图片，**没有任何坐标**。还原需描图,失真。
- **A2 有损矢量瓦片(MVT)**：Mapbox Vector Tile 把坐标**量化到瓦片网格**（精度天然受 `extent` 限制，且按缩放简化）。低缩放下拿到的是粗糙形状,不是同事画的精确边界。比 A1 保留交互+矢量清晰度。

**优点**：唯一能让 network trace 拿不到原始几何的办法；**顺带大幅提性能**（瓦片小、可 CDN/边缘缓存，直接解决 §load-test 里 /dubai/areas 672KB 的痛点）。
**代价**：① 需要瓦片生成（建库时离线生成,或用 `pg_tileserv`/`Martin`/`tippecanoe` 之类）；② **区域点击交互**要单独处理（见 §4）。

### 方案 B —— 加密 GeoJSON 负载（用户想要的版本，**正确做法 + 诚实定位**）

如果坚持「发矢量但 network 看不到明文」，正确实现是**对称加密 + 鉴权取密钥**，不是非对称：

1. 后端有一个 **auth-gated** 端点 `GET /api/areas/key`（要登录/带 session token/过 CF 校验）返回当轮 AES 密钥（短期、可轮换）。
2. `/api/dubai/areas` 返回 **AES-GCM 加密的 boundary**（其余字段明文）。
3. 前端取密钥 → 解密 → 喂给地图。
4. 密钥每 N 小时轮换（配合预渲染缓存按 key 版本失效）。

**诚实定位**：这只挡 T1、给 T2 加几小时麻烦。**不要对它有安全幻觉**。而且：
- 加了 per-request 解密 CPU（前端）+ 取密钥往返；
- 与「边缘缓存 /dubai/areas」冲突（加密+鉴权就没法 CDN 公共缓存了）；
- 仍可从渲染后的地图 source 直接读出明文几何（必须配合 §4 让前端**也不持有完整明文** → 否则纯属自欺）。

> B 单独做价值有限。若选 B，务必配 §5 的限流+CF+水印,否则就是花力气装样子。

### 方案 C —— 周边硬措施（**无论 A/B 都该做，便宜有效**）

- **开限流**（现 `index.ts:86/92` 是关的）：按 IP/session 限 `/dubai/areas` 等的频率 → 直接掐掉批量爬。**性价比最高的一招**。
- **Cloudflare Bot Fight Mode / WAF**：你已在 CF，后台开关，挡自动化爬虫。
- **几何水印 / 蜜罐**：在多边形里嵌入**人眼不可见的微小顶点扰动**，且**每个 session 略有不同** → 一旦在竞品站看到你的形状，能**法律举证是从谁那泄露的**。这是对 T3 唯一真正有威慑力的技术手段。
- **ToS + DMCA**：条款明确禁止抓取/转载，是对竞品的最终后盾。

## 4. 交互难点：区域点击（A 档的主要代价）

区域块现在是**可点的**（点区 → 弹 area-insights）。瓦片化后前端没有矢量多边形,点击命中要换法：

- **C1 服务端命中**：点击 → 拿屏幕经纬度 → `GET /api/areas/at?lng=&lat=` → 服务端 `ST_Contains(boundary, point)` 返回 areaId。**零几何下发**，最干净。每次点一下一个轻量请求。
- **C2 低精度命中几何**：只给前端一份**大幅简化/量化的多边形**（`ST_SimplifyPreserveTopology` 到很粗）用于本地命中检测——**粗到偷了也没用**，但够判断点在哪个区。省一次网络往返。
- **C3 MVT 自带命中**：方案 A2 的矢量瓦片本身可 `queryRenderedFeatures` 命中,但那等于又把（有损的）几何给了前端——介于 A 和 B 之间。

推荐 **A1 栅格 + C1 服务端命中**：network 里既无坐标、点击也不下发几何，保护最强；性能也最好。

## 5. 推荐路线（分期，待决策后 pickup）

- **Phase 0（先做，1 天，纯收益不碰几何）**：开限流 + CF Bot 防护 + ToS 条款。挡住 T1 大半、防滥用、保护性能。**无论后面选啥都要做。**
- **Phase 1（真保护 + 真提速，推荐）**：方案 **A1 栅格瓦片 + C1 服务端点击命中**。离线生成区域瓦片 → raster source 叠加 → 删除 /dubai/areas 的 boundary 下发。一并解决 672KB 性能痛点。
- **Phase 1'（替代，若必须保留前端矢量交互）**：方案 **A2 MVT 有损瓦片**，接受「粗糙几何可被拿到」。
- **Phase 2（威慑 T3）**：几何水印 + 蜜罐（每 session 扰动 + 泄露溯源）。
- **不推荐单独做方案 B（前端加密）**：性价比低、与缓存冲突、仍可从渲染层读出；除非有非做不可的产品理由。

## 7.5 决策落定（2026-06-27）

经过 Luna tour 依赖分析，**最终方案定了，瓦片化全部排除**：

- ❌ **栅格瓦片**：废掉 area block 的「切指标重染色」(`TimelineEngine.ts:529` areaMetric) 和「高亮某区」(collab select 'area')，直接坏 Luna tour 叙事。出局。
- ❌ **MVT 矢量瓦片**：按视口分块加载 = Luna 飞镜头时「一块一卡 load」(pop-in)，违反硬约束；且对 ~180KB 的小数据集是过度工程，多一套瓦片管线要维护。出局。
- ✅ **维持「一次性预加载的 geojson 矢量源」并做瘦**（已实现）：`ST_SimplifyPreserveTopology`(11m) + 坐标 5 位小数。672KB→540KB raw / 180KB→127KB gzip，截图验证形状无走样、Luna 零 pop-in、切指标/高亮全保留。env 可调 `AREA_SIMPLIFY_TOLERANCE` / `AREA_COORD_DIGITS`。

**几何仍下发（交互的物理前提）→ 防盗彻底走「不碰几何」路线**：限流(已上线) + CF Bot + 几何水印溯源 + ToS。瓦片化不再考虑。

## 8. 一句话结论

「后端加密、前端解密、定期轮换」**给不了你要的保护**（公钥解密=零保密；任何客户端解密都能被绕过）。要让 **network trace 真的拿不到坐标**，唯一有效的是**根本不把坐标发给前端**——服务端瓦片化（方案 A），它还顺手解决了 /dubai/areas 的性能问题。前端加密(方案 B)只是障眼法,不建议单独做。**先做 Phase 0(限流+CF+ToS)**，再按威胁等级决定要不要上瓦片+水印。
