# Luna Tour —— 手机端「疯狂颤抖」+ 开场运镜重做

日期：2026-07-29 · 目标页：`https://www.pinzos.com/?toursession=demo`

Owner 原话：

> 我现在的luna tour体验极差 在手机版会疯狂颤抖 而且一开始的动作也不好
> 他要高一点 围着迪拜缓慢旋转边介绍 帮我完整优化 特别是手机版 desktop版也要考虑
> 优化这个script 不能有颤抖 动作要好 要集中中间屏幕能看到重要信息

---

## 0. 先做了一件事：把「颤抖」变成可测的数字

以前每次改运镜都只能「改完请 owner 用真机看」。这次先写了三个我自己能跑的脚本
（都在 `frontend/scripts/`）：

| 脚本 | 干什么 |
|---|---|
| `tour-jitter.mjs` | 手机/桌面两个尺寸真跑一遍 tour，逐帧记录相机 + 帧间隔，输出 fps / 长帧占比 / **单帧屏幕位移** / 方向反转 / long task |
| `tour-profile.mjs` | CDP 采样 profiler，按 self-time 排序「谁在偷主线程」 |
| `tour-layers.mjs` | 运镜中地图上到底挂了几层、哪些层带 zoom 插值（每帧都要 recalculate）、地标/项目 pin 还在不在 |

两个关键设计（都是踩坑之后加的）：

- **`--dist=dist`**：把 `https://www.pinzos.com` 的静态资源劫持成本地 `dist/`，
  但 origin 仍是生产域名 → 后端 API / CORS / 瓦片全走真实生产，唯一变的是前端代码。
  这样「改一行 → 立刻知道数字变好还是变坏」。（直接开 `localhost:4173` 不行：
  生产 API 不认这个 origin，tour 直接「网络错误」。）
- **内部 visitor id + 429 告警**：跑了十几轮之后匿名地图额度被烧光，
  `/api/dubai/landmarks`、`/api/dubai/areas` 全 429 → **地标和区域图层压根不上地图**，
  页面变轻、fps 虚高。我一度据此得出「优化让它变慢了」的错误结论。
  现在跑分固定用一个内部 visitor id（mapMeter 豁免、且被排除在所有分析口径外），
  并且只要出现 429 就在输出里大喊「这一轮不能用」。

还有一条：**单轮数字不能信**。同一份代码连跑三轮，fps 能在 19 和 31 之间摆
（卫星瓦片网络延迟 + 本机负载）。所以加了 `--runs=N` 取中位数。

## 1. 诊断结论

### 「疯狂颤抖」不是相机算错，是**掉一帧就猛拽一次**

相机是**时间的函数**：`camera = f(clock)`，每帧 `jumpTo` 到采样值。这套本身是丝滑的
（方向反转数≈0，证明没有两个东西在抢相机）。但只要某一帧迟到 300~1000ms
（手机上瓦片解码 / GC / 合成器一忙就迟到），**下一帧会把这段时间的位移一次性补完** ——
实测单帧跳 **156px**。眼睛看到的就是一记猛拽；连着掉几帧就是「疯狂颤抖」。

实测（390×844 / DPR3 / CPU×4，真实客户地图）：旧版单帧最大位移 **156.4px**，
长帧（>33ms）占比 **87.8%**。

### 谁在偷帧

profiler + 图层普查的结论，按贡献排序：

1. **区域名标签在开场糊成一片**。tour 期间碰撞检测是关掉的（理由是「环绕时每帧重排
   placement 会周期性打嗝」），当时的假设是「tour 的 zoom 下画面里只有几个标签」——
   **假设是错的**：建立机位在 zoom≈9.9，画面里挤了三四十个中文区域名，层层叠在一起，
   顺便把三个项目 pin 全埋了。既贵又丑。
2. **俯角 45° 的城市级全景**。俯角每高一度，朝地平线铺出去的远景瓦片就更多；
   而且实测 pitch 34 / zoom 9.9 时**画面下面一半多是空沙漠**，
   三个项目被挤到上面三分之一 —— 正是「要集中中间屏幕能看到重要信息」的反面。
3. **layout 属性依赖 zoom**。`lt-props-sym` 的 `icon-size`、氛围层的 `icon-size` 都写了
   zoom 插值。运镜每帧 zoom 都在变 → MapLibre 每帧重算这些层的 symbol 布局，
   而且图标自己在微缩放（卡片在动的地图上**自己抖**）。
4. **氛围层 15Hz `setData`**。那不是「改个坐标」，是 序列化→worker→重建 geojson 索引→
   重算 symbol 布局→回主线程。profiler 里 worker `receive` 排到第三。
5. **`raiseTourLayers()` 的 moveLayer 风暴**。每进一拍，四个 sink 各调一次，每次又带 6 次
   重试 → 一拍 100+ 次 `moveLayer`，**全都落在镜头刚要起飞的那一刻**。
6. **`maxTileCacheSize={600}`**。600 张 256×256 卫星栅格 ≈ **157MB 显存**。
   桌面无感，手机（尤其 iOS）会撞 GPU 内存上限。
7. **脉冲圈每帧两次 `setPaintProperty`**，而它是 1.7 秒一轮的呼吸动画。

顺带排除了两个我原本怀疑的：**React 重渲染不在 profile 前 40 名**（`maybeEmit` 的
12fps 节流是有效的）；**MapLibre 5.18 没有 `setPrefetchZoomDelta`**（那是 mapbox 的 API，
它压根不做父级预取），所以降落那几秒的密集长帧就是真正需要的瓦片，没有冗余请求可砍。

### 「一开始的动作也不好」——剧本里的开场根本没有环绕

prompt 明写着「cut 到建立机位，然后**缓慢高空环绕**」。demo 实际生成的是：

```
[ keyframe zoom 10.2 (瞬切), keyframe zoom 11.2 (2.5s 推近) ]
```

一个**静止广角**，然后推近 1 级 zoom，全程 bearing 不动。而开场旁白约 19 秒，
引擎会把相机轨道时间伸缩到旁白长度 → 那 1 级 zoom 被摊到 19 秒，画面基本是静止的。

另外两个隐形 bug：

- 桌面的建立机位一直被 `MIN_TOUR_ZOOM = 10.8` **悄悄夹紧**（后端算的是 10.2），
  所以桌面从来没真正拍到过那张城市全景。
- **赶路段也被旁白拉长**。一段本该 2.5 秒到位的 flyover，配 20 秒旁白被拉成
  **11 秒的空中平移** —— 画面里没有任何信息，而且正是这几秒在手机上疯狂拉新瓦片。
- 开场那张大标题卡**没有 `duration_ms`**，而「没有 duration」= 留到这一拍结束
  = 在三个项目 pin 上面挂 19 秒。

## 2. 改了什么

### 运镜 / 构图

| 改动 | 文件 |
|---|---|
| **开场机位与运镜改成按几何算死，不再交给 AI**：高空（比剧本再退 0.35 级）+ 65° 缓慢环绕，转多久由旁白长度决定（≈3.4°/秒）。收尾同样退到高空慢慢转 | 新增 `engine/openingShot.ts`，`TourOverlay` 里覆盖 `intro`/`outro` 的 camera |
| **开场俯角 45°→ 手机 20° / 桌面 26°**：构图回到「所见即所算」，不再半屏沙漠；顺带砍远景瓦片 | `openingShot.ts` |
| **`MIN_TOUR_ZOOM` 放宽**（手机 8.6 / 桌面 9.4），解除对建立机位的夹紧 | `engine/cameraTrack.ts` |
| **相机 padding**：对准的是「扣掉章节条和字幕之后**看得见的那块**」的中心，不是画布中心。设一次，之后每帧 `jumpTo` 自动沿用 | `mapTourHandle.setViewportPadding()` + `TourOverlay` |
| **赶路不许被旁白拉长**（`rigid` 段），多出来的时间全部给停留吸收 | `cameraTrack.ts` 的 `rigid` / `remap()` / `wallDuration()`，引擎改用 `camTargetMs` |
| **手机端俯角上限 48°→38°、抛高上限 2.2→1.2 级** | `cameraTrack.ts` |
| **标题卡默认只停 5.5 秒**（剧本没写 duration 时） | `TimelineEngine.DEFAULT_OVERLAY_MS` |

### 抖动 / 每帧成本

| 改动 | 文件 |
|---|---|
| 🔴 **单帧位移上限 45px**：迟到就慢慢追，永远不许一帧跨过 45px。落后看不出来，猛拽看得出来 | `TimelineEngine.applyCamera()` |
| tour 里**区域名出现门槛推后 2.2 级** —— 开场全景干净无标签，镜头下降才浮出来 | `MapViewMapLibre` `area-label-text` filter |
| **地标名字参加碰撞检测**（只有 15 个，开销可忽略），图标仍永远显示；**项目 pin 占位**，地标名字自己让开 | `MapViewMapLibre` + `mapTourHandle` |
| `lt-props-sym` / 氛围层的 `icon-size` **去掉 zoom 插值** | 同上 |
| 氛围层 15Hz → 桌面 8Hz / 手机 5Hz | `map/ambientLife.ts` |
| `raiseTourLayers`：顺序**已经对就一次 moveLayer 都不做**；多次调用合并成一次；重试 6→3 | `mapTourHandle.ts` |
| 脉冲圈 `setPaintProperty` 60Hz → 12Hz | `mapTourHandle.ts` |
| 窄屏 `maxTileCacheSize` 600 → 140（157MB → ≈37MB 显存） | `MapViewMapLibre` |

### 后端

`tour-generator.ts` 的 prompt 明说：**开场/收尾的相机由 app 计算并覆盖**，
模型只需给建立机位那一个关键帧（让 storyboard 读得通），精力放在旁白上。

## 3. 结果（3 轮中位数，390×844 / DPR3 / CPU×4，真实客户地图）

| 指标 | 旧 | 新 |
|---|---|---|
| fps | 16.4 | **19.2** |
| 长帧 >33ms 占比 | 87.8% | **56.4%** |
| **单帧最大位移** | **156.4px** | **44.2px** |
| long task | 190ms/s | 168ms/s |

单帧位移那一行是**代码保证**，不是测出来的运气：限幅器不可能让它超过 45px。
这条直接掐死了「掉一帧 = 一记猛拽」的机制，也就是 owner 说的「疯狂颤抖」。

而且新版是在**做更多运镜**的前提下更顺的 —— 旧版开场几乎静止（静止的地图当然不掉帧），
新版整个开场都在真正环绕。

桌面（1440×900 / DPR2 / 不降速，2 轮中位数）：

| 指标 | 旧 | 新 |
|---|---|---|
| fps | 53.2 | 49.0 |
| 长帧 >33ms | 0.4% | 1.2% |
| **单帧最大位移** | **299.4px** | **45px** |

桌面本来就不掉帧，但**那一记 299px 的猛拽桌面也有** —— 只是被 60fps 掩盖成「闪一下」。
少掉的 4 fps 是因为新版整个开场都在真正环绕（旧版几乎静止），这个交换是值得的。

CPU×4 是很狠的降速（模拟低端机）；owner 自己的手机会好不少。

**上线后在生产上复测（同配置，3 轮中位数）**：

| | 手机 | 桌面 |
|---|---|---|
| fps | 37.4 | 48.8 |
| 长帧 >33ms | 9.2% | 1.1% |
| 单帧最大位移 | 44.1px | 45px |
| long task | 80ms/s | 4ms/s |

（比本地 `--dist` 那轮更好，是因为本机当时还在跑构建。）
后端 `tour-e2e.ts` 31/31 通过 —— prompt 改动没有影响内容生成。

## 3b. 第二轮（owner 真机复核之后）

上线后 owner 在 Android Chrome 上看到三个新问题，都修了。

### ① 贴底的东西被浏览器裁掉（项目卡切一半，CC/喇叭整个消失）

地图容器在 `h-screen`（=100vh）里，而**手机浏览器的 100vh 是「地址栏收起时」的大视口**。
地址栏和系统导航栏一露出来，页面底部那一条就在可见区域之外 —— `bottom: 12px` 的项目卡
被切掉约 40px，`bottom: 14px` 的 CC/喇叭按钮**一个都看不到**。

修在**一处**：`.lt-tour-host` 不再 `inset: 0`，而是把底边收到真正看得见的那条线上：

```css
bottom: calc(var(--lt-hidden-bottom, 0px) + env(safe-area-inset-bottom, 0px));
```

`--lt-hidden-bottom` 由 TourOverlay 用 `visualViewport` 量出来（`host.bottom -
(vv.offsetTop + vv.height)`），地址栏收放时会连续更新。这样一改，**所有 `bottom:`
定位的子元素自动跟着上移** —— 以后新加贴底浮条不用各自记得加偏移（那是「字幕糊在卡片
上」栽三次的老路）。同一个数字也喂给相机 padding，否则相机对准的是一条客户看不见的线。

顺手抓到一个同类问题：暂停时「继续观看」按钮**整块盖死**项目卡。被按钮盖住和被屏幕裁掉
对客户是一回事 → 暂停时收起项目卡（底部已经有三张探索卡讲同样的信息）。

新增 `frontend/scripts/tour-cutoff.mjs`：逐个浮层量「有没有被裁/被互相盖住」，
在「浏览器 UI 吃掉 120px」和「不占位」两种视口下各跑一遍，覆盖欢迎页/开场/到访/暂停四态。

### ② 手机视野太窄，看不完整个迪拜

同 zoom 下可见经度 ∝ 屏幕宽度：桌面 1440px 能看到约 1.1°，手机 390px 只有 0.36° ——
差 3 倍。而「装得下那几个项目」这条规则在手机上算出来恰好就是紧紧框住三个 pin。
加一条**下限**：开场至少要横向看到 0.52°（≈迪拜主城区，棕榈岛 → Downtown → Deira），
不管项目怎么分布。

### ③ 「有时候介绍 project 时地图完全没有在动」

`weakness` 那类拍写的是「关键帧到当前机位」（from == to），再被时间伸缩拉到十几秒旁白
= **死画面**。现在逐段量屏幕位移，几乎没动的段挂上缓慢环绕（14° 摊到整段 ≈0.7°/秒）。
环绕还一律改成**匀速** —— easeInOut 的 20 秒环绕前后各三四秒看起来就是没在动。

⚠️ 这条**推翻了早先「静止就是静止」的判断**（当时删掉 `AMBIENT_ORBIT_DEG` 的理由是
「到了目的地要读信息，不是继续晕」）。owner 明确要求：永远保持舒服的 smooth 运动。
但他嫌的是**快**不是**动**，所以给的是很慢的一圈。

### 同批继续砍抖动

- 焦点圈改**静态**。逐帧 `setPaintProperty` 会强制满帧重绘（连真正静止的时刻都在渲染），
  而我一度节流到 12Hz → 半径每 80ms 跳 3px：**停住的画面里任何抽动都刺眼**，
  而它就长在客户正在盯的那栋楼底下。现在每一拍都保证有运镜了，圈不需要自己"喘气"。
- 氛围层（船/飞机）在 `zoom > 15.5`（它本来就全透明）**一次 `setData` 都不发** ——
  省掉整段项目环节的 symbol 重排（`setData` 会重跑 placement，而 placement 是所有
  symbol 图层一起排的，会连带重排项目 pin 和地标名字）。
- 窄屏 tour `pixelRatio` 1.5 → 1.25。

### 试过但删掉的：自适应匀速节拍

思路是「均匀的 20fps 比忽快忽慢的 8~30fps 好看」，用 EMA 测帧耗时后主动降档匀速下发。
**实测不成立**：cpu×6 下移动频率从 58.8Hz 掉到 30.3Hz，不均匀度只从 2.41 到 2.24 ——
把运动频率砍掉一半，几乎没换到均匀。因为长帧不是「我们要得太勤」造成的，
是卫星瓦片解码/上纹理这类**外部工作**，少要几次重绘不会让它变快。已删除并在代码里留档。

### 第二轮结果（390×844 / DPR3 / **CPU×6**，3 轮中位数）

| 指标 | 第一轮上线版 | 第二轮 |
|---|---|---|
| fps | 27.7 | **47.5** |
| 长帧 >33ms | 39.2% | **6.6%** |
| 画面移动频率 | 34.5Hz | **58.8Hz** |
| 移动间隔不均匀度 | 2.61 | **2.24** |
| long task | 166ms/s | **82ms/s** |
| 单帧最大位移 | 43.1px | 43.2px（限幅仍生效） |

上线后在生产上复测（机器空闲时）：fps 55.7 / 长帧 1.4% / 不均匀度 1.12 / longtask 17ms/s。

**⚠️ 跑分的教训：单轮和两轮的数字都不能信。** 同一份代码，两轮中位数能量出 27.7 和
47.5 两个结果；我曾据两轮差异得出「优化让它变慢了」并差点回滚一批正确的改动。
必须 `--runs=3`。

## 4. 还没解决的 / 下一步

- **剩下的长帧几乎全是卫星瓦片解码+上纹理**，集中在两处：①环绕时新瓦片扫进画面；
  ②降落那 2~3 秒跨 5 级 zoom。MapLibre 没有可关的冗余预取，能砍的只有「少跨 zoom」
  和「转慢一点」，两者都已经压过一轮。真要再进一步只有两条路：
  提前预热目标机位的瓦片 URL（省网络，不省解码），或者换 512 瓦片（省 3/4 数量，
  代价是清晰度对半 —— **这是产品决策，要 owner 拍**）。
- **真机复核仍然必要**：headless 的 rAF/合成器行为和真手机不一样，
  尤其 iOS Safari 的 GPU 内存与 `100vh`。
- 字幕在手机上偶尔 4 行、顶到底部卡片；`chunkCaption` 的 58 字上限可以再收。
